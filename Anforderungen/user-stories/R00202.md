# User Story R00202 — Commit-Verweise an der Karte hinterlegen und entfernen (API)

Als Agent der Factory, der an einer Karte baut und nach seinem Bericht die dabei entstandenen Commits festhält,
möchte ich die Hashes über die API an die Karte hängen und falsche wieder entfernen,
damit Reviewer und Mensch später sehen, welche Arbeit zu der Karte gehört — schon während sie auf dem Kartenzweig liegt.

Ausgangslage jeder Story (herstellbar mit Git und der API): Arbeits-Repository R mit K1, K2 auf `main`, Worktree auf `karte/1` mit W1, Anwendung `kd` im Register auf R; Board „fabrik“ mit #1 in „Entwicklung“ ohne Commits. Beispiele, Schreibweise `<K1>`/`<K1:7>` und Zahlen wie in [R00202](../R00202-commit-verweise-an-der-karte-hinterlegen-und-entfernen.md).

## US-1: Commit mit Kurz-Hash hinterlegen

- **Gegeben** #1 ohne Commits, die Commit-Zahl des Board-Ordners ist n
- **Wenn** der Agent `entwickler` `POST /api/aufgaben/1/commits` mit `{commits: ["kd:<K1:7>"]}` sendet
- **Dann** antwortet die API mit 200, die Datei von #1 trägt unter `commits` die Zeile `- kd:<K1>` mit vollem Hash, die Commit-Zahl ist n+1 mit `entwickler` als Autor, und `GET /api/aufgaben/1` liefert `commits: ["kd:<K1>"]`

## US-2: Commit vom Kartenzweig im Worktree hinterlegen

- **Gegeben** W1 liegt nur auf `karte/1` im Worktree, nicht auf `main`
- **Wenn** der Agent `POST` mit `["kd:<W1:7>"]` sendet
- **Dann** antwortet die API mit 200, und `kd:<W1>` steht an #1

## US-3: Wiederholung ändert nichts

- **Gegeben** `kd:<K1>` steht an #1, die Commit-Zahl ist n
- **Wenn** der Agent denselben Aufruf wie in US-1 noch einmal sendet und danach `["kd:<K1>", "kd:<K2>"]`
- **Dann** antwortet die API beide Male mit 200; nach dem ersten Aufruf ist die Commit-Zahl n, nach dem zweiten n+1, und #1 trägt `kd:<K1>`, `kd:<K2>` je einmal

## US-4: Falscher Verweis wird abgewiesen, nichts geschrieben

- **Gegeben** #1 ohne Commits, die Commit-Zahl ist n
- **Wenn** der Agent nacheinander `["xy:<K1>"]`, `["kd:0000000"]` und `["kd:<K2>", "kd:0000000"]` sendet
- **Dann** antwortet die API jedes Mal mit 400 und `{fehler, verweis}` (zuletzt `verweis: "kd:0000000"`), die Commit-Zahl bleibt n, und `GET /api/aufgaben/1` liefert `commits: []` — auch `kd:<K2>` steht nicht da

## US-5: Ein Angriff über den Verweis erreicht Git nicht

- **Gegeben** der Server läuft mit `GIT_TRACE=<datei>`, #1 ohne Commits
- **Wenn** jemand `["kd:--output=x"]`, `["kd:3f2a9c1;rm -rf x"]` und `["kd:3f2a 9c1"]` sendet
- **Dann** antwortet die API jedes Mal mit 400, es entsteht keine Datei `x`, R ist unverändert (`git status --porcelain`), und die Spur der Git-Aufrufe enthält keinen der drei Texte

## US-6: Verweis entfernen, auch wenn das Repository fehlt

- **Gegeben** an #1 stehen `kd:<K1>` und `kd:<K2>`; danach wird R umbenannt
- **Wenn** der Mensch `sh` `DELETE /api/aufgaben/1/commits/kd:<K1:7>` sendet und danach `DELETE …/kd:0000000`
- **Dann** antwortet die API zuerst mit 200 und genau einem Commit, `GET` liefert nur noch `["kd:<K2>"]`; der zweite Aufruf ergibt 404 ohne Commit

## US-7: Bestehende Dateien bleiben verlustfrei

- **Gegeben** #1 trägt `commits` mit `kd:<K1>`, dem unlesbaren Eintrag `kd:zz` und einem Hash aus lauter Ziffern; #2 ist eine alte Datei ohne `commits`
- **Wenn** der Mensch die Titel von #1 und #2 ändert — einmal mit diesem Stand und einmal mit dem Stand vor dieser Karte
- **Dann** sind beide Aufgaben nicht defekt; `commits` von #1 steht in beiden Fällen zeichengleich in der Datei, `GET` liefert die drei Einträge wörtlich; #2 bekommt keinen Schlüssel `commits` und liefert `commits: []`
