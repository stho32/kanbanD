# User Story R00203 — Commit-Verweise nach einem Rebase ersetzen (API)

Als Agent der Factory, der den Kartenzweig auf `main` rebased und danach die Hashes seiner Karte nachziehen will,
möchte ich alle alten Verweise mit einem Aufruf durch die neuen ersetzen, jeden an seinem Platz,
damit die Karte nach dem Rebase auf die richtigen Commits zeigt, ohne dass Verweise verloren gehen oder verwaisen.

Ausgangslage jeder Story (herstellbar mit Git und der API): Arbeits-Repository R mit K1, K2, K3, K4 auf `main`, Worktree auf `karte/1` mit W1, Anwendung `kd` im Register auf R; Board „fabrik“ mit #1 in „Entwicklung“, an der `kd:<K1>`, `kd:<W1>`, `kd:<K2>` in dieser Reihenfolge stehen; Agent `entw1`, Mensch `sh`. Beispiele, Schreibweise und Zahlen wie in [R00203](../R00203-commit-verweise-nach-einem-rebase-ersetzen.md) und [R00202](../R00202-commit-verweise-an-der-karte-hinterlegen-und-entfernen.md).

## US-1: Nach einem Rebase nachziehen

- **Gegeben** der Worktree wurde mit `git rebase main` neu aufgesetzt, W1 heißt jetzt `<W1'>`; die Commit-Zahl des Board-Ordners ist n
- **Wenn** der Agent `entw1` `POST /api/aufgaben/1/commits/ersetzen` mit `{ersetzungen: [{alt: "kd:<W1>", neu: "kd:<W1'>"}]}` sendet
- **Dann** antwortet die API mit 200, `kd:<W1'>` steht an der Stelle von `kd:<W1>` (Platz 2), `kd:<W1>` steht nicht mehr an #1, die Commit-Zahl ist n+1

## US-2: Mehrere Paare, ein Commit, Plätze bleiben

- **Gegeben** an #1 stehen `kd:<K1>`, `kd:<W1>`, `kd:<K2>`, die Commit-Zahl ist n
- **Wenn** der Agent `{ersetzungen: [{alt: "kd:<K1:7>", neu: "kd:<K3:7>"}, {alt: "kd:<K2:7>", neu: "kd:<K4:7>"}]}` sendet
- **Dann** antwortet die API mit 200, `GET /api/aufgaben/1` liefert `["kd:<K3>", "kd:<W1>", "kd:<K4>"]` (volle Hashes, Platz 2 unberührt), die Commit-Zahl ist n+1 mit `entw1` als Autor

## US-3: Wiederholung ändert nichts

- **Gegeben** der Aufruf aus US-2 ist schon gelaufen, die Commit-Zahl ist n
- **Wenn** der Agent ihn nach einem Abbruch noch einmal sendet, auch nachdem R umbenannt wurde
- **Dann** antwortet die API mit 200, die Commit-Zahl bleibt n, und #1 trägt weiter `kd:<K3>`, `kd:<W1>`, `kd:<K4>` je einmal

## US-4: Ein falsches Paar verhindert alles, nichts wird geschrieben

- **Gegeben** an #1 stehen `kd:<K1>`, `kd:<W1>`, `kd:<K2>`, die Commit-Zahl ist n
- **Wenn** der Agent nacheinander sendet: `K1 → K3` mit `K2 → kd:0000000` (gibt es nicht); `K1 → K3` mit `V1 → K4` (V1 steht nicht an der Karte); `K1 → K2` (beide stehen an der Karte); `K1 → K3` mit `K3 → K4` (Kette); `K1 → K3` mit `K1 → K4` (doppelt)
- **Dann** antwortet die API mit 400, 404, 409, 400 und 400 und je `{fehler, verweis}`, die Commit-Zahl bleibt n, und #1 trägt unverändert `kd:<K1>`, `kd:<W1>`, `kd:<K2>` — auch `K1 → K3` aus dem ersten Paar steht nirgends

## US-5: Ein Angriff über den Verweis erreicht Git nicht

- **Gegeben** der Server läuft mit `GIT_TRACE=<datei>`
- **Wenn** jemand `{alt: "kd:<K1>", neu: "kd:--output=x"}` und `{alt: "kd:3f2a9c1;rm -rf x", neu: "kd:<K3>"}` sendet
- **Dann** antwortet die API jedes Mal mit 400, es entsteht keine Datei `x`, R ist unverändert, und die Spur enthält keinen der Texte

## US-6: Verwaiste und gelöschte Verweise lassen sich nachziehen, Bestand bleibt verlustfrei

- **Gegeben** an #1 stehen `kd:<V1>` (kein Zweig erreicht ihn), `kd:<V2>` (aus R gelöscht), `kd:zz` (unlesbar) und der Ziffern-Hash `1234567890123456789012345678901234567890`
- **Wenn** der Agent `V1 → K3` und `V2 → K4` sendet
- **Dann** antwortet die API mit 200 und einem Commit, die neuen Hashes stehen auf den Plätzen 1 und 2, `kd:zz` und der Ziffern-Hash stehen wörtlich dahinter, und die Datei ändert sich sonst nicht; das Arbeits-Repository sah `<V1>` und `<V2>` nie
