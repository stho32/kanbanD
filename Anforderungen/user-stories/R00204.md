# User Story R00204 — Commit-Liste einer Karte per API lesen

Als Reviewer-Agent der Factory, der eine Karte prüft, deren Commits auf einem Kartenzweig, auf `main` oder nach einem Rebase auf keinem Zweig liegen,
möchte ich mit einem Aufruf zu jedem hinterlegten Verweis Titel, Autor, Datum, Umfang und Zustand samt Zweigen lesen,
damit ich ohne Zugriff aufs Repository sehe, was an der Karte hängt, wo es liegt und welche Verweise nachzuziehen sind.

Ausgangslage jeder Story (herstellbar mit Git und der API): Arbeits-Repository R mit K1 bis K4 auf `main`, Worktree `R-karte-1` auf `karte/1` mit W1, ein verwaister Commit V1, ein Commit R1 nur auf `refs/remotes/o/x`, ein gelöschter Commit V2, Anwendung `kd` im Register auf R; Board „fabrik“ mit #1, an der `kd:<K3>`, `kd:<W1>`, `kd:<V1>`, `kd:<V2>`, `kd:<R1>` stehen; Agent `entw1`, Mensch `sh`. Beispiele, Schreibweise und Zahlen wie in [R00204](../R00204-commit-liste-einer-karte-per-api-lesen.md), [R00203](../R00203-commit-verweise-nach-einem-rebase-ersetzen.md) und [R00202](../R00202-commit-verweise-an-der-karte-hinterlegen-und-entfernen.md).

## US-1: Fünf Zustände auf einen Blick

- **Gegeben** die Ausgangslage
- **Wenn** der Agent `GET /api/aufgaben/1/commits` aufruft
- **Dann** antwortet die API mit 200 und fünf Einträgen: `kd:<K3>` `auf_zweig` mit `zweige ["main"]` und `entfernte_zweige ["o/main"]`, `kd:<W1>` `auf_zweig ["karte/1"]`, `kd:<V1>` `verwaist`, `kd:<R1>` `auf_zweig` mit `entfernte_zweige ["o/x"]`, `kd:<V2>` `fehlt` zuletzt; K3 trägt „c.txt anlegen“, „Ada Autorin“, `2026-03-01T10:00:00+01:00`, plus 3, minus 0, eine Datei

## US-2: Nach dem Rebase erkennt die Liste, was nachzuziehen ist

- **Gegeben** der Worktree wurde mit `git rebase main` neu aufgesetzt und `kd:<W1'>` ist hinterlegt
- **Wenn** der Agent die Liste liest
- **Dann** steht `kd:<W1>` als `verwaist` und `kd:<W1'>` als `auf_zweig ["karte/1"]` da; nach dem Merge nach `main` und dem Löschen von `karte/1` steht `kd:<W1'>` als `auf_zweig ["main"]`

## US-3: Zweiglisten bleiben lesbar

- **Gegeben** ein Commit, den 11 lokale und 12 entfernte Zweige erreichen
- **Wenn** der Agent die Liste liest
- **Dann** nennt jede Liste zehn Zweige alphabetisch, und `zweige_weitere` ist 3

## US-4: Ein kaputter Verweis verdirbt die anderen nicht

- **Gegeben** an #1 stehen zusätzlich ein Verweis auf eine nicht mehr registrierte Anwendung, einer auf einen fehlenden Ordner und einer ohne Kürzel ohne Standardanwendung
- **Wenn** der Agent die Liste liest
- **Dann** antwortet die API mit 200, diese drei stehen mit `anwendung_unbekannt`, `repository_fehlt` (mit `grund`) und `anwendung_unbekannt` hinter den anderen, die fünf aus US-1 sind unverändert

## US-5: Lesen blockiert nichts und hängt nicht

- **Gegeben** ein Git, das 60 s schläft und ein Kind startet
- **Wenn** der Agent die Liste liest und währenddessen ein Mensch den Titel von #1 ändert
- **Dann** gelingt die Titeländerung in unter 1 s, die Liste antwortet nach 10 bis 15 s mit 503, danach läuft kein Prozess mehr, und nichts wurde geschrieben

## US-6: Auch große Repositories antworten schnell

- **Gegeben** ein Repository mit 20.000 Commits und 50 Zweigen ohne `commit-graph` und eine Karte mit 30 Verweisen
- **Wenn** der Agent die Liste kalt liest
- **Dann** antwortet die API im 95. Perzentil von 20 Läufen in unter 200 ms; ein zweiter Aufruf ohne bewegten Zweig startet kein `--contains`, nach einem bewegten Zweig stimmt der Zustand wieder

## US-7: Handarbeit und feindliche Repositories führen nichts aus

- **Gegeben** von Hand geschriebene Einträge wie `kd:--output=x`, `kd:$(touch x)`, `kd:<K1>^{tree}` und einer mit Zeilenumbruch, dazu ein Arbeits-Repository, dessen Konfiguration `diff.external`, `core.fsmonitor` und `gpg.program` auf Skripte setzt, und ein Commit mit `<script>` im Titel
- **Wenn** der Agent die Liste liest
- **Dann** sind die Einträge `unlesbar` mit wörtlichem `verweis`, keine Datei `x` entsteht, keines der Skripte läuft, der Titel steht als Text in der Antwort, und die gültigen Einträge daneben sind unverändert

## US-8: Bestand und Schreiben bleiben unberührt

- **Gegeben** Dateien, die die Vorversion mit 0, 1, 2, 5 und 30 Einträgen unter `commits` zurückgeschrieben hat
- **Wenn** der Agent die Liste liest
- **Dann** antwortet die API mit 200 und so vielen Einträgen, wie die Datei trägt; die Datei und die Commit-Zahl des Board-Ordners bleiben gleich, und `GET /api/aufgaben/1` startet weiter kein Git
